# 判官 Prompt 撰寫規範（編輯 `prompts/*.md` 時載入）

7 支初判 prompt（`00_polarity` + `01_C-1`~`06_C-6`）＝ Prompt-as-Source 唯一真相源。
硬性項目由 `prompt_source.validate()`（存檔閘門）與 `backend/tests/test_prompt_lint.py` 強制，
**改壞會存不了檔**；本檔說明規則本身與判準。

## 一、架構前提（決定了所有規則的理由）

六域**全部平行執行**（`domain_router.enabled=false`），每域只判自己，且六支 `<domain_boundary>`
結尾都有：

> 「命中任一『不命中』情形時，該問題不輸出歸因，**也不討論它應該屬於哪裡**——那不是本判官的事。」

→ **覆蓋率完全取決於每個域的「判定範圍」寫得夠不夠寬。** A 域說「不屬本項」而沒有 B 域認領，
該類反饋就六域皆棄權、落進 non_issue、**零報錯**。補這種洞的正解是**加寬目標域的判定範圍**，
不是在來源域加指路（各域看不到彼此，指路對判決毫無作用）。

## 二、三條硬禁令（`validate()` 直接拒絕存檔）

1. **禁引他域 code**（L1c）：單域 prompt 內不得出現他域 `C-x-y`。域內 facet 互指允許。
2. **禁「不屬本項」無指涉**（L1a，以「；」切分支判定）：該分支必須有本域 code，否則「本項」
   沒有指涉對象，判官只能讀成「換同域另一個 facet 試試」——這是 false positive 的直接引擎。
3. **禁詞**（L1e）：
   - `取最核心、最直接的` —— 與 `<judgment_rules>`「列出所有明確命中、最多 3 條」正面矛盾。
     Schema `maxItems:3` 已是硬上限；收斂該在合流層（`prejudge._attrs_pack`）做，單域先自我
     壓縮會讓合流層拿不到候選且不可還原。要壓多報去調 `_gate_attrs` 閾值。
   - `且…已合理／正常／成功` —— **不可從原文驗證的正向前提**，與各域「不以常識推定」衝突，
     且預設方向偏向免責。一律改負向測試：「**且原文未指出**…有失職」。

## 三、措辭三詞制

| 句式 | 使用條件 |
|---|---|
| `改由本域〈中文名〉（C-x-y）判定，不歸本項。` | 同域確有承接 facet，**且該 facet 判定範圍逐字含關鍵語彙**（沒有就先去補語彙）|
| `不屬本域、棄權。` | 同域無 facet 承接。**該分支禁止出現任何 code** |
| `不構成問題點、不歸因。` | 該情境**根本不是問題**（商家做對了、純禮貌用語）——與「有問題但不屬我」語義不同 |

拿不準第二與第三種 → 問「這件事有人做錯嗎？」有 → 第二種；沒有 → 第三種。

## 四、預設方向宣告（處理不可觀察事實）

歸因只能取決於**原文說了什麼**，不能取決於**事實真相是什麼**。當判準依賴一個原文通常不會
明說的事實（商家有沒有應變、旅客有沒有看清楚、該項目是否真實存在），必須宣告預設方向：

> **原文未自承／未指明 A 時，不預設 A 成立，該情境預設歸屬為 B。**

範本（全稿寫得最好的兩條，互相咬合）：
- `C-6-6`：「旅客**未自承**沒看而僅現場被規則卡住（**不預設**旅客已理解）→非本項」
- `C-4-2`：「旅客**未自承**漏看條款時，**不預設**他已理解規則，優先視為系統流程把人卡住」

⚠️ 特別注意**卸責方向**：C-6 的 action 是 `escalate_ux`，把商家失職誤判成旅客主觀等於對客戶
不公且讓真問題降級。凡是會把責任推向旅客的判準，一律以「旅客自承」為門檻。

## 五、例證配額（測試強制）

每個 facet 四項全硬斷言：`✅ ≥ 2`、`❌ 總數 ≥ 3`、**`❌ 域外棄權 ≥ 2`**、`❌/✅ ≤ 2.5`。

**第三項才是健康指標。** 六域全平行、每域只判自己，facet 唯一的防誤收工具就是**域外反例**；
域內指路（`→ C-x-y`）只是在同一個域裡搬椅子，不構成防護。

⚠️ **「域外棄權」認的是結論逐字為「不屬本域、棄權」（三詞制第二式）**，第三式「不構成問題點、不歸因」
不算——它說的是「這根本不是問題」，不是「這是別人的問題」，零防誤收能力。
（2026-08-10 踩過：判準原本只看「該行不含本域 code」，C-3-7 靠**兩條逐字重複的第三式**湊過 ≥2，
而它正是嚴重度最高、應觸發供應商管理／法務關注的 facet。）

⚠️ **同一 facet 內禁止逐字重複的例句**（含「同一例句、換句話說結論」）——重複零判別力，只會灌滿配額。

`❌/✅ ≤ 2.5`：比值過高會讓判官對該 facet 過度保守。（實例：C-3-4 曾是 3✅:9❌，而三個域都指路過來
卻收不到，過度保守正是漏收成因。原本只是建議值、無人擋，實測 C-2-3 到 3.00、C-6-2 到 2.67 才補成硬斷言。）

## 六、boundary ↔ facet 雙向完備

`<decision_process>` 明示「從 `<facet_catalog>` 選最貼切的一條 l2_code」＝**判官選碼時讀的是
facet 層**，`<domain_boundary>` 是讀完就丟的前導文。所以：

- boundary 每條「→ 本域（C-x-y）」，被指名 facet 的**判定範圍必須逐字含關鍵語彙**
- boundary 每條 ✅ 命中，至少要有一個 facet 的 ✅ 例對應
- boundary 每條 ❌ 不命中，**1:1 指派**到最容易誤收它的那個 facet，該 facet 要有對應 ❌ 例
- boundary ✅ 的關鍵語彙**不得**同時出現在同域某 facet 的 ❌ 例結論中（自我矛盾）

**boundary 的一行交辦撐不住整個類別**——寫了交辦就要去 facet 層補語彙與例句。

## 六之二、新增／擴充成立型態時的五層下放檢查（**頭號復發缺陷**）

到 2026-08-10 為止，三輪對抗審查各自都抓到同一個模式：**新規則只寫進定義層，沒下放到執行層**，
結果該類反饋在執行時必然棄權、規則形同具文。第二輪 15 條存活 finding 有 8 條屬此類。

新增或擴充任何「成立型態」（本域現在多收哪一種問題）後，**逐層核對五個位置，缺一即算未完成**：

| 層 | 位置 | 沒改的後果 |
|---|---|---|
| L1 | `<attribution_domain>` 判定範圍／核心判準 | 型態根本沒被宣告 |
| L2 | 歸因原則「只抽取…的問題」＋「若…即棄權，不替它找歸屬」 | **反向否決**新型態 |
| L3 | `<domain_boundary>` 收束句「判準永遠回到同一個問題：…」＋【核心鐵則】 | 鐵則的封閉列舉把新型態排除 |
| **L4** | **`<decision_process>` 第 3 步** | **判官逐點執行的就是這一問；沒涵蓋＝100% 棄權** |
| L5 | facet 判定範圍逐字語彙 ＋ 至少一條 ✅ | 選碼時無錨點、信心被壓低 |

⚠️ **同一行內的前後半也要一起看**：L1 常寫成「必須出在 A**或** B 才屬本域。只要不是 A，一律不屬本域」——
前半加了 B、後半沒改，等於當場撤銷。（實例：`04_C-4_platform.md:20` 效期第二型態、
`03_C-3_supplier.md:42` 外溢防線撤銷 C-3-4 的預設方向宣告。）

⚠️ **L4 若原本是「只問一件事」，新增型態後必須改成明確的雙問並以「兩問皆否才棄權」收尾**，
不要只在原句塞進一個「或」——判官對複合單問的執行一致性明顯低於逐項雙問。

## 六之三、語義判準禁寫成字面清單（尤其禁列多語表面形式）

判準若本質是**語義的**（「這件事發生了沒有」「指控的對象是誰」），就用語義描述，**不要列表面字串清單**。

2026-08-10 連兩輪被同一件事咬：polarity 的「建議型 vs 已發生落差」原本寫成中／日／英三語的字彙清單，結果
① 第二輪把反事實過去式（`〜あれば良かった`／`I wish there were…`）誤列進「未來取向」那半邊；
② 第三輪補的反事實判準又和同一行的建議型清單互斥。改成「本次已具備、只是希望更多 → 建議型；
本次確實缺少或未達成 → 已發生的遺憾」後，該行從 603 字降到 400 字，且不再需要維護平行清單。

三個失敗模式：
- **沒列到的語言沒覆蓋**——清單永遠不完整，而反饋是多語的
- **平行清單互相矛盾**——同一概念在三語各寫一次，改一處必漏兩處
- **判官改用字面比對**——這正是 C-1-5 把英文 `info sheet` 回譯後撞進「說明」白名單的成因

例外：**機器契約**（`## Taxonomy` 的 code、Schema 的 enum）本來就是字面比對，不適用本條。
若真需要語言提示，只寫一句「**非中文反饋一律以語義判定，不與本行的中文字面比對**」，不列詞表。

## 六之四、刪除類改動：邏輯冗餘 ≠ 行為冗餘

判官受**詞彙錨點**驅動，不只受邏輯涵蓋驅動。**一行即使在語義上是另一條的真子集，只要它是某組主題詞
在該檔的唯一出現處，刪掉就會讓那組主題失去判別線索。**

2026-08-11 實例：C-6 的「時長／費用／停留／集合等主題 → 分辨是客觀失職（非本域）還是主觀不滿（屬本域）」
被判定為「被同檔核心判準嚴格涵蓋」而刪除——該提案通過了五道對抗性檢驗（逐字比對、真子集推導、
合成反饋逐點跑 decision_process、認領語彙 grep、配額重數）。金標實測後三條新失敗全部往 C-6-3 跑，
主題正是被刪那行點名的「集合」「時長」。回退後立刻消失。

**動手前問的不是「這條規則有沒有被涵蓋」，而是「這行有沒有引入別處沒有的具體詞彙」。**

驗證要求（缺一不可）：
- 刪除類改動**必須跑金標實測**，子代理的對抗性放行不能取代量測——它抓得到邏輯矛盾與引文造假，
  抓不到「邏輯冗餘但行為承重」。
- **看誤差分佈，不是看總分**。該次總分 85.6% → 82.2%，形式上仍在 n=30 的 13pp 噪音帶內、單看數字會放行；
  但三條新失敗**同一個去向、同一組主題**——失敗案例在「錯成哪一碼」上聚集 ⇒ 真退步，不是抖動。

**成本效益**：整批冗餘清理只省 0.9% 字元，而 token 有 94% 走 cached prefix（半價），
省下的錢在誤差範圍內。除非是明確雜訊（變更紀錄、導航括號、多語詞表），否則不值得為此冒靜默漏判。

## 七、機器契約（不得改動）

- **`## Taxonomy`**：分類唯一源。域機器值、中文名、action、owner、evidence_gated 全在 root；
  Schema 的 `l2_code.enum` 由它**於 load 時派生注入**（prompt 不手寫 code 清單）。改它＝改分類體系，
  會連動 DB、歷史對比、前端篩選。
- **`## Schema`**：六域逐位元組相同，`maxItems: 3`。
- **`00_polarity` 的 Schema**：`polarity.enum` 必須**恰為** `SENTIMENT_BANDS` 的三個 key（集合相等，
  少一個或多一個都擋）。理由：`prejudge` 對非三態值的處置是**靜默降級為 neutral**、無日誌，
  而 neutral 在 `attribute_when` 內 → 錯誤會一路無聲滲進歸因。

## 八、六域共用區塊

`<judgment_rules>` / `<abstain_rules>` / `<critical_rules>` / `<output_format>` / `<limitations>`
六域**逐位元組相同**（測試強制）。改一支就要六支一起改，否則判準分裂且不會報錯。

**`<decision_process>` 是半共用**：五步之中第 1／2／4／5 步六域逐字相同（鎖死），
**只有第 3 步是域專屬**。有意讓某域的固定步分歧時，登記 `_ALLOWED_STEP_DIVERGENCE` 並寫理由；
該 dict 帶雙向斷言——登記了卻其實沒分歧也會紅，防過期例外靜默解鎖。

另有兩條跨檔鎖：`<domain_boundary>` 的 ⚠️ 標頭與收束句（收束句必須是該區塊**最後一個非空行**，
用「是最後一行」而非「有出現」，否則有人在收束句之後追加裁定會全綠、而那條裁定已降格成附註）；
以及六域的**區塊出現順序**（C-1 專屬的 `<evidence_gate>` 除外）。

⚠️ **第 3 步另有一條反向斷言：六域兩兩相異。** 真正會發生的不是「有人單獨改了第 4 步」，
而是**複製既有檔當模板**時第 3 步留著來源域的問句——那是該域執行層完全失效，
但輸出仍 schema 合法、仍非空、**零報錯**，沒有別的機制抓得到。

⚠️ **這些鎖守的是漂移，不是品質，而且偵測不到〈六之二〉的根因 A**：新規則寫進 L1/L3 卻沒下放
第 3 步時，第 3 步與自己上一版逐字相同、與其餘五域仍相異，所有斷言全綠。別把「骨架有測試」
讀成「執行層安全」。另外 `validate()` 只拿得到單支檔，跨檔一致性做不成存檔閘門——
熱編路徑仍可改裂，只有 CI 跑 repo 檔才會紅。

⚠️ **不要引入 include／模板展開機制**——那會打破「人直接編輯 md」的 Prompt-as-Source 初衷，
RuleManager 熱編時看不到實際內容。維護重複由測試鎖，不由抽象解。

## 九、選填區塊

`<evidence_gate>`（只 C-1 有）、`跨域外溢防線`（只 C-3 有）等屬**選填**，按域的實際需要加，
不強求六域齊平——硬塞空區塊只是噪音。必備區塊清單見 `test_prompt_lint._DOMAIN_REQUIRED_TAGS`。

## 十、發版與驗證（改完必做）

**改 `prompts/*.md` 不會自動上線。** `prompt_source.load()` 是 DB active 優先、檔案 fallback：

```
rule_versions.reset_rule_default('prompt_C-N')   # 讀檔存為新 active 版
```

驗證發版是否生效：比對 `judge_rule_version_lst` 的 `rule_content->>'text'` 與檔案內容**逐字元相等**。

跑 eval 前**必須先發版**（`eval_prompt_single.py` 無 `--versions`，永遠讀 DB active，不發版就是
測到舊版而且不會報錯）。改動方向決定判準，詳見 `prompts/BASELINE.md`：

| 改動類型 | 通過判準 |
|---|---|
| 零變化（格式、同義改寫）| 全指標 ±0.10 內，**且逐案 improvements/regressions 清單為空** |
| 收斂（收緊界線、修措辭）| 多報率↓ 或 棄權正確率↑；命中率不得跌出噪音帶 |
| 擴張（補覆蓋盲區）| **BASELINE 失效**（參照集是舊 prompt 的產物，新增的正確歸因會被算成多報）→ 走 `eval_equivalence.py` 版本 pin 雙跑，或查「負向但六域全棄權」的靜默漏判池單向驗證 |
